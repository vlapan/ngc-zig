## Completed
- **Radix Sort for Events**: Implemented `radixSortEvents` in `src/flatten.zig` to replace `std.mem.sort`. Fixing shift casting (`u5`/`u7`), `const` buffer syntax, and stable `is_end` partitioning.
- **Result**: REGRESSION. +165M instructions (+10.3%), +84M cycles (+16.2%), +21.8 MB RSS (+35.8%). Phase 1 time increased from 101ms to 133ms.
- **Root cause**: 4-8 passes over data with intermediate buffers (indices, event_buffer, counts) cause memory bandwidth bottleneck and extra allocations. `std.mem.sort` (Introsort) is cache-friendly and in-place.
- **Decision**: Rejected. `std.mem.sort` remains optimal.

- **Result**: -928M instructions (-52.4%), -399M cycles (-66.2%), -28.1 MB RSS (-34.0%). Phase 1: 133ms → 16ms. Phase 2: 44ms → 28ms. Output identical to baseline.
- **New module**: `src/cidr.zig` with 11 TDD tests covering IPv4/IPv6 edge cases, HOLE handling, private IP skipping, full range, non-aligned ranges.
- **Static overrides**: Now handled by sweep-line (size=0 wins priority). Tracked via `FlattenStats.overrides`.

- **SWAR CSV tokenization**: Created `src/swar.zig` with `findByte()` (8-byte-at-once byte search). Replaced `std.mem.indexOfScalar` in `parser.zig` with SWAR version. 12 TDD tests covering edge cases (boundaries, short strings, multiple matches, chunk transitions).
- **Result**: -22.9M instructions (-2.7%), -6.0M cycles (-2.9%). I/O & Parsing: 51ms → 48ms. Wall-clock: marginal (0.08s → 0.07s). Output identical to baseline.
- **Algorithm**: XOR 8-byte chunk with replicated needle, detect zero bytes via `(chunk - 0x0101...) & ~chunk & 0x8080...`, use `@ctz` for position. Fallback to linear scan for tail < 8 bytes.
- **Assembly verified**: Clean ReleaseFast output, no bounds checks in hot loop.
- **`findTwoBytes` evaluated**: Single-pass helper to find first two occurrences. Found slightly slower (+3M instructions) than two `findByte` calls for short CSV lines (~30-40 bytes). Nested match-tracking overhead outweighs single-pass benefit when commas span different 8-byte chunks. Kept in module for other use cases.

## Multi-Threading Evaluation (Rejected)

### Proposal
Parallelize IPv4 and IPv6 pipeline streams using `std.Io.concurrent` to achieve wall-clock reduction.

### Architecture Designed

```
Main Thread                    Worker Thread 1 (IPv4)           Worker Thread 2 (IPv6)
────────────                   ──────────────────────           ──────────────────────
Parse static file
  ├─ static_v4_ranges ───────► Parse v4 CSV
  └─ static_v6_ranges ───────► Flatten segments                 Parse v6 CSV
                                 Generate CIDRs                   Flatten segments
                                 Write to v4_buf                  Generate CIDRs
                                                                  Write to v6_buf
  ◄──────────────────────────────────────────────────────────────────────────────────
  Join both futures
  Write: static_v4 → v4_buf → static_v6 → v6_buf (to file)
  Aggregate stats, print telemetry
```

### Zig 0.16.0 API Verification
- `std.Thread.Pool` **REMOVED**. Use `std.Io.concurrent` / `std.Io.Group` instead.
- `ArenaAllocator` is now **thread-safe and lock-free** (no per-thread arenas needed).
- `heap.ThreadSafeAllocator` **REMOVED** (no longer needed).
- `init.io` is `Io.Threaded` by default (real OS threads).

### Re-evaluated Performance Estimate

| Metric | Sequential | Parallel (realistic) | Gain |
|--------|------------|---------------------|------|
| Wall-clock | 80ms | ~68-72ms | **-10-15%** |
| Instructions | 841M | 841M | 0% |
| RSS | 54.5 MB | ~70-85 MB | **+28-56%** |

**Why original 35-45% estimate was wrong:**
- Assumed entire pipeline was parallelizable. It's not.
- Static parsing, setup, output writing, and final flush are sequential (~15ms overhead).
- I/O contention: both threads reading files simultaneously may slow down parsing.
- 50ms (62.5%) is I/O-bound, not CPU-bound. Parallelizing compute won't speed up file reads.
- Only ~30ms of actual compute is parallelizable (Flatten + CIDR Gen overlap).

### Complexity Introduced

| Component | Lines | Complexity |
|-----------|-------|------------|
| `PipelineResult` struct | 15 | Low |
| Worker function (`processStream`) | 60 | Medium |

**Additional complexity:**
- Race condition testing and determinism verification
- Memory buffer OOM handling
- Platform-specific `io.concurrent` availability
- Debugging concurrent code is significantly harder than sequential

### Cost-Benefit Analysis

| Factor | Value |
|--------|-------|
| Time saved per run | ~10ms |
| Lines of code added | ~165 |
| RSS increase | +15-30 MB |
| Debug complexity | Significantly higher |
| Maintenance burden | Higher (concurrency bugs are subtle) |
| Use case | CLI tool, runs occasionally, already 80ms |

### Decision: Rejected

**10ms savings for 165 lines of complexity and 30% more RAM is not justified.** The tool runs in 80ms on a hot cache -- already fast enough for a CLI that generates config files occasionally. The cost-benefit ratio is unfavorable.

### When to Reconsider

Multi-threading becomes worthwhile if:
1. **Dataset grows 10x+**: If CSV files grow to millions of rows and runtime exceeds 500ms.
2. **Real-time use case**: If this becomes a service that processes requests on-demand (not batch CLI).
3. **Memory is cheap**: If RSS budget increases to 200MB+ and latency is critical.
4. **I/O is eliminated**: If data is pre-loaded in memory (e.g., memory-mapped always resident), making compute the dominant bottleneck.

### SIMD Potential

**Verdict: Almost none.**

| Hot Function | Time | SIMD Potential | Why Not |
|---|---|---|---|
| `fastParseInt` | 9.18ms | Already SWAR | Variable-length numbers separated by commas. SIMD needs fixed-width data. |
| `formatIPv6` | 8.16ms | Low | Branch-heavy (zero-compression, variable hex length). Control flow kills SIMD. |
| `formatIPv4` | 5.74ms | Low | Uses LUT, outputs one-at-a-time to writer. No bulk data. |
| `std.mem.sort` | 8.86ms | Rejected | Introsort is already optimal. SIMD sorting networks lose on cache behavior. |
| `findScalarPos` | 4.29ms | Already SWAR | Lines are ~30-40 bytes. SWAR at 8 bytes covers most of it. |
| `rangeToCidrs` | 3.16ms | None | Bit math with data dependencies. Each iteration depends on the previous. |
| `isPrivateIPv4` | 1.00ms | None | Already single bitwise AND. Called per-segment, not bulk. |

**The fundamental problem:** The pipeline is **streaming**, not **batch**. Each CSV line is parsed, flattened, formatted, and written sequentially. SIMD thrives on bulk uniform data (e.g., "process 1024 IPs at once"). The data is:
- Variable-length (CSV lines differ in size)
- Control-flow heavy (branching on country codes, zero compression, CIDR alignment)
- Output-bound (formatted CIDRs go to a writer one at a time)

### Decision: Stop

SWAR has extracted ~95% of what's possible without changing the streaming architecture. The remaining 1-2% would require:
1. Restructuring into batch processing (major architectural change)
2. Pre-computed format tables for IPv6 (memory vs CPU trade-off)
3. Vectorized output buffering (complexity for <3ms gain)

**Pipeline is now fundamentally limited by I/O and control flow, not byte scanning.**
