## Multi-Threading Evaluation (Rejected)

### Proposal
Parallelize IPv4 and IPv6 pipeline streams using `std.Io.concurrent` to achieve wall-clock reduction.

### Architecture Designed

```
Main Thread                    Worker Thread 1 (IPv4)           Worker Thread 2 (IPv6)
────────────                   ──────────────────────           ──────────────────────
Parse static file
  ├─ static_v4_ranges ───────► Parse v4 CSV
  └─ static_v6_ranges ───────► Flatten segments                 Parse v6 CSV
                                 Generate CIDRs                   Flatten segments
                                 Write to v4_buf                  Generate CIDRs
                                                                  Write to v6_buf
  ◄──────────────────────────────────────────────────────────────────────────────────
  Join both futures
  Write: static_v4 → v4_buf → static_v6 → v6_buf (to file)
  Aggregate stats, print telemetry
```

### Zig 0.16.0 API Verification
- `std.Thread.Pool` **REMOVED**. Use `std.Io.concurrent` / `std.Io.Group` instead.
- `ArenaAllocator` is now **thread-safe and lock-free** (no per-thread arenas needed).
- `heap.ThreadSafeAllocator` **REMOVED** (no longer needed).
- `init.io` is `Io.Threaded` by default (real OS threads).

### Re-evaluated Performance Estimate

| Metric | Sequential | Parallel (realistic) | Gain |
|--------|------------|---------------------|------|
| Wall-clock | 80ms | ~68-72ms | **-10-15%** |
| Instructions | 841M | 841M | 0% |
| RSS | 54.5 MB | ~70-85 MB | **+28-56%** |

**Why original 35-45% estimate was wrong:**
- Assumed entire pipeline was parallelizable. It's not.
- Static parsing, setup, output writing, and final flush are sequential (~15ms overhead).
- I/O contention: both threads reading files simultaneously may slow down parsing.
- 50ms (62.5%) is I/O-bound, not CPU-bound. Parallelizing compute won't speed up file reads.
- Only ~30ms of actual compute is parallelizable (Flatten + CIDR Gen overlap).

### Complexity Introduced

| Component | Lines | Complexity |
|-----------|-------|------------|

**Additional complexity:**
- Race condition testing and determinism verification
- Memory buffer OOM handling
- Platform-specific `io.concurrent` availability
- Debugging concurrent code is significantly harder than sequential

### Cost-Benefit Analysis

| Factor | Value |
|--------|-------|
| Time saved per run | ~10ms |
| Lines of code added | ~165 |
| RSS increase | +15-30 MB |
| Debug complexity | Significantly higher |
| Maintenance burden | Higher (concurrency bugs are subtle) |
| Use case | CLI tool, runs occasionally, already 80ms |

### Decision: Rejected

**10ms savings for 165 lines of complexity and 30% more RAM is not justified.** The tool runs in 80ms on a hot cache -- already fast enough for a CLI that generates config files occasionally. The cost-benefit ratio is unfavorable.

### When to Reconsider

Multi-threading becomes worthwhile if:
1. **Dataset grows 10x+**: If CSV files grow to millions of rows and runtime exceeds 500ms.
2. **Real-time use case**: If this becomes a service that processes requests on-demand (not batch CLI).
3. **Memory is cheap**: If RSS budget increases to 200MB+ and latency is critical.
4. **I/O is eliminated**: If data is pre-loaded in memory (e.g., memory-mapped always resident), making compute the dominant bottleneck.
