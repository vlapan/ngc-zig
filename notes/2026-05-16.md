## Multi-Threading Evaluation (Rejected)

### Proposal
Parallelize IPv4 and IPv6 pipeline streams using `std.Io.concurrent` to achieve wall-clock reduction.

### Architecture Designed

```
Main Thread                    Worker Thread 1 (IPv4)           Worker Thread 2 (IPv6)
────────────                   ──────────────────────           ──────────────────────
Parse static file
  ├─ static_v4_ranges ───────► Parse v4 CSV
  └─ static_v6_ranges ───────► Flatten segments                 Parse v6 CSV
                                 Generate CIDRs                   Flatten segments
                                 Write to v4_buf                  Generate CIDRs
                                                                  Write to v6_buf
  ◄──────────────────────────────────────────────────────────────────────────────────
  Join both futures
  Write: static_v4 → v4_buf → static_v6 → v6_buf (to file)
  Aggregate stats, print telemetry
```

3. **Memory is cheap**: If RSS budget increases to 200MB+ and latency is critical.
4. **I/O is eliminated**: If data is pre-loaded in memory (e.g., memory-mapped always resident), making compute the dominant bottleneck.

### SIMD Potential

**Verdict: Almost none.**

| Hot Function | Time | SIMD Potential | Why Not |
|---|---|---|---|
| `fastParseInt` | 9.18ms | Already SWAR | Variable-length numbers separated by commas. SIMD needs fixed-width data. |
| `formatIPv6` | 8.16ms | Low | Branch-heavy (zero-compression, variable hex length). Control flow kills SIMD. |

| `std.mem.sort` | 8.86ms | Rejected | Introsort is already optimal. SIMD sorting networks lose on cache behavior. |
| `findScalarPos` | 4.29ms | Already SWAR | Lines are ~30-40 bytes. SWAR at 8 bytes covers most of it. |

| `isPrivateIPv4` | 1.00ms | None | Already single bitwise AND. Called per-segment, not bulk. |

**The fundamental problem:** The pipeline is **streaming**, not **batch**. Each CSV line is parsed, flattened, formatted, and written sequentially. SIMD thrives on bulk uniform data (e.g., "process 1024 IPs at once"). The data is:
- Variable-length (CSV lines differ in size)
- Control-flow heavy (branching on country codes, zero compression, CIDR alignment)
- Output-bound (formatted CIDRs go to a writer one at a time)

### Decision: Stop

SWAR has extracted ~95% of what's possible without changing the streaming architecture. The remaining 1-2% would require:
1. Restructuring into batch processing (major architectural change)
2. Pre-computed format tables for IPv6 (memory vs CPU trade-off)
3. Vectorized output buffering (complexity for <3ms gain)

**Pipeline is now fundamentally limited by I/O and control flow, not byte scanning.**

## Single Config File Design (Explored)

### Proposed Format
Flat key-value file replacing `--static`, `--groups-file`, `--filters-file`, and all other flags:
```
# NGC Configuration
ipv4=/data/geo-ipv4.csv
ipv6=/data/geo-ipv6.csv

```

### Design Decisions
- **Invocation**: `NGC_CONFIG=config.ngc ngc` or `ngc config.ngc`
- **Repeated keys**: `static=`, `group=`, `filter=` can appear multiple times
- **Comments**: `# comment` lines ignored
- **Static blocks**: Could merge `static.conf` contents here, or keep `static_file={path}` for large lists
- **Parser cost**: ~30 lines, ~2ms startup (file read + parse), zero external dependencies
- **Binary size**: +0 (custom parser uses existing stdlib)
- **Overrides**: CLI args can still override config values when needed

### Parser Sketch (~30 lines)
```zig
fn parseConfig(io: std.Io, path: []const u8, alloc: std.mem.Allocator) !Config {
    var file = try std.Io.Dir.cwd().openFile(io, path, .{});
    defer file.close(io);
    const stat = try file.stat(io);
    const mapped = try std.posix.mmap(null, stat.size, .{ .READ = true }, .{ .TYPE = .PRIVATE }, file.handle, 0);
    defer std.posix.munmap(mapped);

    var config = Config{ .output = "output.conf" }; // defaults
    var it = std.mem.splitScalar(u8, mapped, '\n');
    while (it.next()) |line| {
        const trimmed = std.mem.trim(u8, line, " \t\r\n");
        if (trimmed.len == 0 or trimmed[0] == '#') continue;
        const eq = std.mem.indexOfScalar(u8, trimmed, '=') orelse continue;
        const key = std.mem.trim(u8, trimmed[0..eq], " \t");
        const val = std.mem.trim(u8, trimmed[eq + 1 ..], " \t");
        // key matching: ipv4, ipv6, output, static, group, filter, static_file, etc.
    }
    return config;
}
```

## Zig 0.16.0 Io Concurrency API (Explored)

### Promise-like Pattern
| Zig `Io` | JS/TS Promise | Description |
|---|---|---|
| `io.async(fn, args)` | `new Promise(fn)` | Spawns task, returns `Future(T)` |
| `future.await(io)` | `await promise` | Blocks until completion, returns result |
| `future.cancel(io)` | `AbortController` | Cancels running task |
| `std.Io.Group` | `Promise.all()` | Manages many tasks, awaits all at once |
| `io.concurrent(fn, args)` | N/A | Same as `async` but **guarantees** parallelism |

### Key Difference from Promises
- `Future` is **not** automatically scheduled on a thread pool
- It's a handle to a task that the `Io` implementation runs
- `Io.Threaded` (default) → real OS threads
- `Io.Evented` (experimental) → stack switching (green threads)
- Same API, different backend

### Example Pattern
```zig
var group: std.Io.Group = .init;
defer group.cancel(io);
group.async(io, processV4, .{...});
group.async(io, processV6, .{...});
try group.await(io); // Promise.all equivalent
```

### Relevance to This Project
- Multi-threading was rejected (10ms savings for 165 lines + 30% RSS)
- But the `Io` API is already available and could be used later if:
  - Dataset grows 10x+
  - Becomes a real-time service
  - Memory budget increases

## Nginx Binary Geo File Format (Explored)

### Overview
Nginx's `ngx_http_geo_module` can load a pre-compiled binary cache (`.bin`) instead of parsing text CIDRs on every reload. The binary is mmap'd directly into memory with a single pass of pointer relocation.

### Binary File Layout
```
+---------------------------+  Offset 0
| ngx_http_geo_header_t     |  16 bytes
|  GEORNG + version + CRC32 |
+---------------------------+
| Deduplicated value nodes  |  Variable (rbtree-style)
| (ngx_http_variable_value_t|  Each country string stored once
|  + string data)           |
+---------------------------+
| Null value sentinel       |  16 bytes (data=NULL terminator)
+---------------------------+
| Pointer array             |  0x10000 * 8 = 512KB (64-bit)
| (offsets, not pointers)   |  Indexed by ip >> 16
+---------------------------+
| Range bucket 0..65535     |  Arrays of ngx_http_geo_range_t
| (ngx_http_geo_range_t)    |  Terminated by { value: NULL }
+---------------------------+
```

### Header (16 bytes)
```c
typedef struct {
    u_char    GEORNG[6];      // Magic: 'G','E','O','R','N','G'
    u_char    version;        // 0
    u_char    ptr_size;       // sizeof(void*): 4 or 8
    uint32_t  endianness;     // 0x12345678
    uint32_t  crc32;          // CRC32 of everything after header
} ngx_http_geo_header_t;
```

### Key Design: Offset-Based Pointers
All "pointers" are stored as **offsets from the mmap base**, not absolute addresses. On load, Nginx does a single pass adding the base address to each offset. This makes the file position-independent and instantly usable after mmap.

### Range Entry (16 bytes on 64-bit)
```c
typedef struct {
    ngx_http_variable_value_t *value;  // 8 bytes (offset)
    u_short start;                     // 2 bytes
    u_short end;                       // 2 bytes
} ngx_http_geo_range_t;                // 12 + 4 padding = 16 bytes
```

### Country Value Deduplication
Country strings are stored once in an rbtree-like structure, referenced by offset. All ranges pointing to "US" share the same value node. ~250 unique countries = ~250 value nodes, not 1M.

### Auto-Loading Mechanism
Nginx config:
```nginx
geo $country {
    ranges;
    include /etc/nginx/geo-ipv4;
}
```
Nginx automatically tries `/etc/nginx/geo-ipv4.bin` first. If valid (magic, CRC32, newer than text file), uses binary. Otherwise falls back to text. No config change needed.

### Generation Conditions
Binary is only generated by Nginx when:
1. `ranges` mode enabled (first directive in geo block)
2. `entries > 100,000`
3. Only 1 include file
4. No "outside entries" (ranges don't cross /16 boundaries)
5. No mixed entries (binary + text)

### Limitations
- **IPv4 only**: Binary format only supports `ranges` mode which is IPv4-specific
- **No IPv6 binary**: `ngx_radix128tree_t` has no binary serialization
- **Platform-dependent**: Pointer size and endianness baked into file

### Implementation Opportunity
We could generate the `.bin` file directly alongside the text output:
```
CSV → NGC → geo-ipv4.conf + geo-ipv4.bin + geo-ipv6.conf
```
Nginx would automatically pick up the binary for IPv4. IPv6 stays as text CIDR.

**Effort**: ~200 lines. We already have the flattened segment data in the right structure after sweep-line. Just need to serialize it into the binary format.

**Benefit**: Nginx reload time drops from seconds (text parse + tree build) to milliseconds (mmap + pointer relocation).

### Split IPv4/IPv6 Nginx Config Pattern
Since binary format is IPv4 only, the recommended Nginx config splits them:
```nginx
# Fast IPv4 (binary)
geo $geo_v4 {
    ranges;
    include /etc/nginx/geo-ipv4;
}

# IPv6 (text, unavoidable)
geo $geo_v6 {
    include /etc/nginx/geo-ipv6.conf;
}

# Combined lookup
map $binary_remote_addr $country {
    default $geo_v4;
    "~^[0-9a-f:]+$" $geo_v6;
}
```

Our tool would output three files:
- `geo-ipv4.conf` (text CIDR, fallback)
- `geo-ipv4.bin` (binary cache, auto-loaded by Nginx)
- `geo-ipv6.conf` (text CIDR, no binary option)

## Nginx RAM Footprint Verification (2026-05-16)

### Problem
The original heuristic (`56B/v4, 72B/v6`) was derived from source code struct analysis only. It estimated ~61 MB for 1M CIDRs. Actual measurements showed ~99 MB.

### Profiling Setup
Created `test/nginx-profile/` with:
- `profile.sh` — automated script: starts nginx, measures RSS, sends 55 unique IPs via curl (`?ip=` param), reports timing and memory, kills nginx
- `nginx-baseline.conf` — nginx without geo rules (6.1 MB baseline)
- `nginx-full-foreground.conf` — nginx with geo rules (includes `../output.txt`)
- Uses `daemon off;` + `-p` prefix for correct relative path resolution and accurate RSS measurement

### Results

| Metric | Baseline | Full (1M CIDRs) | Delta |
|--------|----------|-----------------|-------|
| RSS | 6.1 MB | 98.8 MB | **92.7 MB** |
| Avg server time (TTFB - Connect) | 0.146ms | 0.147ms | **0.001ms** |
| Per-CIDR memory | N/A | N/A | **96.68 bytes** |

### Why the Original Estimate Was Wrong
1. **Only counted struct size, not allocation patterns** — Each CIDR creates 2-3 unique radix tree nodes, not 1
2. **Node struct on 64-bit**: 4 pointers (left/right/parent/value) = 32 bytes per node
3. **Pool fragmentation**: `ngx_palloc()` aligns to pointer size, pools have internal fragmentation beyond 16B
4. **Value storage**: `ngx_http_variable_value_t` per unique country (~24B, deduplicated)
5. **96.68B = ~32B/node × ~2.5 nodes/CIDR + pool overhead + value storage**

### Updated Heuristic
- Changed `src/nginx.zig`: `bytes_per_ipv4 = 97`, `bytes_per_ipv6 = 97` (unified)
- IPv4/IPv6 difference is negligible — same `ngx_radix_node_t` struct on 64-bit
- Platform note: 32-bit would be ~50B/CIDR (pointers are 4 bytes)
- Linux vs macOS: slight variation in pool allocator (~5-10%)

### Geo Lookup Performance
- **Zero measurable latency impact** — 0.001ms difference across 55 unique IPs
- Radix tree lookup over 1M CIDRs is O(log n) with tiny constant, effectively free
- No caching: each unique IP resolved independently with consistent timing
- `volatile` flag: unnecessary for our use case (single `$country` reference per request)

## Conventions & Process Improvements (2026-05-16)

### Session Handoff Protocol
When session ends abruptly or normally:
1. Save all state files (`knowledge/`, `notes/`)
2. Push any committed changes to origin
3. Write final entry to today's note with: what was done, what's pending, any blockers
4. If mid-task: note exact file/line where work stopped, next step to take
5. Never leave uncommitted changes that would be lost

### Error Handling Conventions
- **Error unions** (`!void`, `!T`) for recoverable errors: file not found, parse failures, network issues
- **`catch unreachable`** only for mathematically impossible conditions (e.g., `std.SemanticVersion.parse` on known-valid version string)
- **`catch {}`** (silent ignore) only for non-critical cleanup operations
- **Error messages**: lowercase, no trailing period, specific about what failed and why
- **Fail vs Warn**: Fail on invalid input that would produce wrong output. Warn on deprecated configs or recoverable issues.
- **CLI errors**: print to stderr, exit with code 1, show usage hint if relevant

### Naming Conventions
- **Modules**: `snake_case.zig` (e.g., `parser.zig`, `cidr.zig`)
- **Public functions**: `camelCase` (e.g., `estimateRamBytes`, `parseArgs`)
- **Private functions**: `camelCase` with leading underscore if internal helper (e.g., `_parseLine`)
- **Constants**: `snake_case` (e.g., `bytes_per_ipv4`), `SCREAMING_SNAKE_CASE` for sentinel values (e.g., `HOLE`)
- **Types/Structs**: `PascalCase` (e.g., `FlattenStats`, `IPRange`)
- **Test functions**: `snake_case` with descriptive name (e.g., `test "nginx.estimateRamBytes: zero counts"`)
- **Variables**: `snake_case` for locals, `camelCase` for function params

### Module Documentation Conventions
- All `pub` functions, structs, and constants must have `///` doc comments
- Doc comment format: one-line summary, blank line, detailed explanation if needed
- Include parameter descriptions for non-obvious parameters
- Include return value description for non-obvious returns
- Example:
  ```zig
  /// Estimates Nginx RAM footprint in megabytes.
  ///
  /// Based on actual profiling: 97 bytes per CIDR entry on 64-bit platforms.
  pub fn estimateRamMB(v4_cidrs: usize, v6_cidrs: usize) usize { ... }
  ```
