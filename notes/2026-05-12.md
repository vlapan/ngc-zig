## Profiling Analysis: `make profile` vs `make profile2`
- **`make profile` (`lldb`)**:
  - *Method:* Batches addresses and runs them through `lldb` via `image lookup -a`. Rate is 1,000,000 samples per second.
  - *Output:* Flat list showing a single line per symbol (e.g., `geoip-converter'ip.IpTrie(u32).insertRange + 372 [inlined] ...`).
  - *Pros:* Extremely fast to generate. Great for a dense, high-level overview of the most expensive addresses.
  - *Cons:* Because Zig heavily inlines code in `ReleaseFast`, LLDB's single-line formatting can obscure the full call stack, masking the true context of an expensive instruction.

- **`make profile2` (`atos`)**:
  - *Method:* Iterates over top addresses and passes them individually to macOS's native `xcrun atos -i` symbolication tool. Rate is 100,000 samples per second.
  - *Output:* A fully unrolled, multi-line stack trace for *every single instruction pointer*.
  - *Pros:* Unrolls inlined functions beautifully. We can now clearly see that `mem.swap` inside `sort.block` is being called via `blockSwap` from standard library sorting. We can see `fmt.charToDigit` deeply nested inside `parseInt`. This is infinitely better for deep-diving into Zig's optimized compilation artifacts.
  - *Cons:* MacOS only. Much slower to generate because it spawns an `atos` sub-process for every single instruction address. Lower sample rate (100kHz).

- **Conclusion / When to Use**:
  - Use **`make profile`** for a 5-second quick-check to see if a massive regression occurred or to look at raw instruction offsets.
  - Use **`make profile2`** for serious performance debugging when you need to understand exactly *why* an instruction is hot, especially since Zig's aggressive inlining merges disparate logic into single PC locations.
