### 🧠 KNOWLEDGE_DISCOVERY: Algorithmic limits of BGP data overlaps
Experimentally proved that replacing the `active_ids` O(N) array scan with an O(1) Index Map results in a net negative performance impact (+1.3MB RAM, +5.8M CPU instructions). 
**Why:** Real-world BGP routing datasets have incredibly shallow overlap depths (usually 1-3). Iterating a 3-element `[]u32` array in L1 cache is temporally O(1) and fundamentally faster than the initialization overhead of setting up a mathematically perfect O(1) lookup table spanning 337,000 indices. 
**Caveat:** This rejection is dataset-dependent. Pathological input with deep nesting (50+ overlapping ranges) would make the linear scan a bottleneck. If the tool ever needs to handle such data, the index map or a min-heap should be reconsidered. For real-world GeoIP/BGP data, the simple approach is optimal.

## Performance Optimization Backlog

Explored codebase for performance optimization opportunities. Created a prioritized backlog in `knowledge/tasks.md` with 11 items across 3 tiers.

### Tier 1: High Impact (10-50% speedup)

**1. Eliminate Recursive Trie `insertRange`** (`trie.zig:41-93`)
- **Problem:** Deep recursion on 1M+ nodes causes stack pressure and prevents CPU branch prediction optimization.
- **Approach:** Convert to iterative stack-based traversal using an explicit stack array.
- **Est:** 5-10% Phase 2 speedup.

**2. Replace `active_ids` linear scan with O(1) lookup** (`flatten.zig:53-57`)
- **Problem:** `swapRemove` does O(N) linear search on every event end. With ~330k events, this is O(N^2) worst case.
- **Approach:** Use a small fixed-size hash set or bitset for O(1) removal.
- **Est:** 10-15% Phase 1 speedup.

**3. Direct CIDR output from sweep-line**

### Why the Trie Exists Today
Nginx only accepts CIDR notation (power-of-2 aligned blocks). An arbitrary IP range like `[100, 500, US]` cannot be expressed as a single CIDR -- it must be fractured into multiple aligned blocks. The Trie was originally built to do TWO jobs:
1. **Overlap resolution** -- dirty input ranges collide and nest; the Trie resolves priority by recursively splitting
2. **CIDR fragmentation** -- arbitrary ranges get broken into minimum valid CIDRs via binary tree traversal

### Why the Trie is Now Redundant
The sweep-line pre-flattening (added 2026-05-14) completely handles job #1. After the sweep-line runs, the output is a stream of mathematically perfect, non-overlapping, disjoint segments. The Trie is now only doing job #2, which has a well-known iterative algorithm:

```
fn rangeToCidrs(start, end, country):
    while start <= end:
        max_block = largest power-of-2 aligned block at `start` fitting in [start, end]
        write CIDR(start, max_block, country)
        start += block_size
```

This is a tight loop. Zero allocations. Zero recursion. Produces the identical minimum CIDR set.

### What the Trie Currently Costs
- **Memory:** ~1M+ packed nodes allocated (61MB RSS for the tree alone per telemetry)
- **Recursion depth:** `insertRange` calls itself recursively for every binary split. A single `/0` range spanning the full IPv4 space creates 32 levels of stack frames. Across 1M+ nodes this is significant stack pressure.
- **Two extra passes:** After all insertions, `optimize()` does a full post-order traversal to merge siblings that got fragmented by insertion order. Then `dump()` does a full pre-order traversal to emit output. Three traversals total (insert, optimize, dump) where one would suffice.
- **Static override rework:** After the main dataset is inserted, static ranges are inserted as `HOLE` entries, which punch holes by resetting node countries to MIXED and zeroing children. This is necessary because the Trie doesn't know about static ranges during initial insertion.

### How Sweep-Line Already Handles Static Overrides
Static ranges are currently inserted *after* the main dataset. But they are just another input with highest priority (smallest size wins in the sweep-line). If we feed static ranges into the sweep-line with `country = HOLE` and `size = 0`, they naturally win every collision they participate in. The sweep-line outputs disjoint segments with `HOLE` country already baked in. No post-insertion override pass needed.

### Current Pipeline vs Proposed Pipeline

**Current:**
```
CSV → Parse → Ranges → Sweep-Line → Disjoint [start,end,country]
  → Trie.insertRange() (recursive, allocates 1M+ nodes)
  → Trie.optimize() (post-order traversal)
  → Trie.dump() (pre-order traversal, writes output)
```

**Proposed:**
```
CSV → Parse → Ranges → Sweep-Line → Disjoint [start,end,country]
  → for each segment: rangeToCidrs() (iterative loop, writes output directly)
```

### Telemetry Evidence
From `notes/2026-05-14.md` telemetry:
- Phase 1 (Sweep-Line + stream to Trie): ~136ms
- Phase 2 (optimize + dump only, since insert happens during Phase 1): ~57ms
- But the Trie insert cost is embedded in Phase 1's 136ms. If we separate it, the Trie's total contribution (insert + optimize + dump) is significantly higher than 57ms alone.

The 136ms Phase 1 time includes both sweep-line execution AND streaming insertRange calls into the Trie. The sweep-line itself is fast -- the insertRange recursion is the heavy part. Removing it means Phase 1 becomes pure sweep-line (~14ms from earlier benchmarks before streaming), and Phase 2 disappears entirely.

### Estimated Impact
- **Runtime:** 40-50% total speedup. The Trie is the single largest bottleneck in the current pipeline.
- **Memory:** ~18-20MB RSS reduction (no 1M+ node allocations). Currently at 61.3MB total.
- **Code:** Removes `trie.zig` entirely (~200 lines). Simplifies `main.zig` pipeline logic.
- **Risk:** Moderate. The range-to-CIDR algorithm is well-understood but must handle u128 for IPv6. Static override behavior must be verified to produce identical output.

**4. Multi-threading / Parallel Pipelines**
- **Problem:** IPv4 and IPv6 streams are fully independent but run sequentially.
- **Approach:** Use `std.Thread` to parse+flatten+trie both simultaneously on separate cores.
- **Est:** 35-45% wall-clock reduction.

### Tier 2: Medium Impact (5-10% speedup)

**5. Pre-allocate `active_ids` with known max** (`flatten.zig:38`) -- **INVALIDATED**
- Already `initCapacity(alloc, 64)`. BGP nesting depth is 1-3, so capacity is 20x over-provisioned. Growth never triggers.

**6. Batch writer flushes** (`ip.zig:198-297`, `ip.zig:121-151`) -- **INVALIDATED**
- `formatIPv4`/`formatIPv6` write to a 64KB buffered `std.Io.Writer`. Multiple `writeAll` calls are memcpy into buffer, not syscalls. Flush only when buffer fills. Near-zero impact.

**7. Replace `std.mem.sort` with radix sort for events** (`flatten.zig:31-36`)
- Events are integers (`u32`/`u128`). Radix sort is O(N) vs comparison sort's O(N log N). Sort runs once per IP version, not in a hot loop. u128 radix sort is complex. Marginal gain.
- **Est:** 5-8% Phase 1 speedup (theoretical).

**8. Avoid `@intCast` in hot trie paths** (`trie.zig:38`) -- **INVALIDATED**
- `insertRange` is now iterative. Only remaining cast is `usize`→`u24` in `allocNode`, which is a deliberate 8-byte packing trade-off. Removing it bloats `TrieNode` from 8→10 bytes (+5MB RSS for 2.5M nodes).
